# تجربة (Tajruba)

منصة عربية ثنائية اللغة لقياس تجربة المريض **PREMs**، النتائج الصحية المبلغة من
المريض **PROMs**، وذكاء التعليقات مع استعادة الخدمة (Service Recovery)، مبنية
كمشروع Node.js/TypeScript كامل (خادم + واجهة) بدون أي اعتماد خارجي مدفوع.

## البنية التقنية

- **الخادم**: Express + TypeScript، يعمل عبر `tsx` مباشرة (بدون خطوة بناء منفصلة للخادم).
- **قاعدة البيانات**: SQLite عبر `node:sqlite` المدمجة في Node 22 (ملف واحد، بدون تثبيت خارجي)، بمخطط مصمم للترحيل لاحقًا إلى PostgreSQL + Row-Level Security.
- **الواجهة**: React 18 + React Router + Tailwind CSS v4 + Recharts، مبنية عبر Vite.
- **المصادقة**: جلسات مبنية على كوكي HttpOnly مع تجزئة كلمات المرور بـ `scrypt` (بدون مكتبات جلسات خارجية).
- **الذكاء الاصطناعي للتعليقات**: محلّل قواعد محلي (Rule-Based) لا يرسل أي نص خام إلى أي API خارجي — راجع قسم PDPL أدناه.

```

├── server/
│   ├── db.ts             # مخطط SQLite الكامل (متعدد المستأجرين)
│   ├── types.ts          # الأنواع المشتركة (الأدوار، الخدمات، التصنيفات...)
│   ├── auth.ts           # كلمات المرور، الجلسات، RBAC
│   ├── scoring.ts        # محرك حساب PREMs وPROMs (مع اختباراته)
│   ├── comments.ts       # إخفاء الهوية (PII) + التصنيف والخطورة (مع اختباراته)
│   ├── provisioning.ts   # يبني نسخة مستقلة من بنك الأسئلة/القوالب/PROMs لكل مستشفى جديد
│   ├── seed.ts           # بيانات تجريبية كاملة وقابلة لإعادة التوليد (مستأجر العرض فقط)
│   ├── seed-data/        # بنك الأسئلة، الخدمات الفرعية، أدوات PROMs، مسارات الرعاية (JSON)
│   └── api.ts            # كل نقاط REST API
├── server.ts             # نقطة الدخول (Express + Vite middleware)
├── src/                  # الواجهة (React)
│   └── pages/            # الاستبيان العام + لوحة التحكم بكل أقسامها
```

## ما تم تنفيذه

- **تعدد المستشفيات (Multi-tenancy)**: أي مستشفى يسجّل حسابًا عبر `/register`
  يحصل فورًا على بيئة بيانات مستقلة بالكامل (بنك أسئلة، قوالب، أقسام، أدوات
  PROMs خاصة به) — لا شيء مشترك بين المستشفيات إلا هيكل الكود نفسه.
- تسجيل دخول حقيقي مع صلاحيات RBAC أربعة: `SystemAdmin`، `QualityManager`،
  `DepartmentManager` (مقيّد بقسمه)، `ExecutiveViewer`.
- عزل بيانات كامل حسب `tenant_id` على مستوى كل استعلام (مُختبر بشكل صريح، بما
  فيها اختبار تسجيل مستشفيين مستقلين والتأكد من عدم تقاطع بياناتهما).
- **12 خدمة رئيسية**: 6 خدمات أساسية تطابق تصنيف برامج تجربة المريض الفعلية في
  المستشفيات السعودية (الممارسة الطبية، التنويم، الطوارئ، الجراحة النهارية،
  الرعاية المنزلية، بنك الدم)، بالإضافة إلى 6 خدمات تخصصية (الولادة، الأطفال،
  الغسيل الكلوي، الأورام، التأهيل، العيادة الافتراضية) ببنك أسئلة مخصص لكل
  منها. المختبر والأشعة والصيدلية **ليست خدمات مستقلة** — تظهر كأسئلة مشروطة
  (بوابة نعم/لا ثم أسئلة متابعة) داخل استبيان أي خدمة رئيسية استخدمها المريض
  أثناء زيارته.
- محور **إمكانية الوصول والشمول** (لغة الشرح، الترجمة، الوصول لذوي الاحتياجات
  الحركية، دعم ضعاف السمع/البصر، الاحترام الثقافي والديني) مضاف لكل خدمة من
  الخدمات الست الأساسية.
- بنك أسئلة PREMs أصلي لكل خدمة (استبيان الطوارئ وحده مثلاً 32 سؤالًا شاملة
  الخدمات الفرعية ومحور الوصول والشمول) مع قوالب استبيان جاهزة لكل خدمة.
- استبيان مريض عام عبر رابط برمز (Token) بدون تسجيل دخول، مع دعم أسئلة مشروطة
  (Skip Logic) تظهر/تختفي حسب إجابة سابقة، ودعوات تنتهي صلاحيتها ولا يمكن
  إكمالها مرتين.
- **استبيان هاتفي بمساعدة موظف**: واجهة داخلية لموظف يعبّي الاستبيان نيابة عن
  مريض تم الاتصال به هاتفيًا، بنفس منطق الأسئلة المشروطة.
- **قناة QR / الأجهزة الثابتة (Kiosk)**: رمز قابل لإعادة الاستخدام بلا حد أقصى
  ولا انتهاء صلاحية — يُطبع كملصق QR في القسم أو يُعرض على جهاز لوحي، ويمكن لأي
  عدد من المرضى استخدامه بشكل مجهول دون رقم جوال. يُدار من استوديو الاستبيانات
  مع معاينة رمز QR مباشرة، ولا يخضع لقائمة عدم التواصل أو فترة التهدئة لأنه غير
  موجّه لمريض بعينه.
- محرك حساب PREMs: المقياس الأساسي هو **نسبة Top Box** (بحسب اصطلاح HCAHPS)
  وليس المتوسط من 5، مع مقارنة كل محور بمعيار مرجعي بالنقاط المئوية، بالإضافة
  إلى NPS و% الإجابة بـ"نعم" للأسئلة المشروطة. **موثوقية العينة** بأربع مستويات
  (غير كافية < 30، استرشادية 30-99، موثوقة 100-299، جاهزة للنشر ≥ 300 — نفس عتبة
  CMS لأربعة أرباع متتالية)، وتقارير اتجاه قابلة للتجميع شهريًا/ربع سنويًا/نصف
  سنويًا/سنويًا.
- **إطار أخذ العينة**: قائمة عدم تواصل (Do Not Contact) لكل مستشفى، وفترة
  تهدئة 90 يومًا تمنع دعوة نفس رقم الجوال مرتين خلالها — تُدار من الإعدادات.
- ذكاء التعليقات: إخفاء تلقائي للهوية (جوال، هوية وطنية، رقم ملف، بريد إلكتروني)
  **قبل** أي تحليل، ثم تصنيف وتحليل مشاعر وخطورة (1-5)، مع تنبيه فوري للخطورة ≥ 4.
- استعادة الخدمة (Service Recovery): دورة حياة موثّقة جديد ← مُسند ← تحت المعالجة
  ← مغلق، وإغلاق الحالة يتطلب صلاحية إدارة تجربة المريض (متطلب توثيق CBAHI).
- **حلقة تواصل مغلقة اختيارية**: عند ترك المريض ملاحظة (عبر رابط الاستبيان أو
  الاستبيان الهاتفي)، يمكنه الموافقة صراحةً على أن يتواصل معه المستشفى بخصوص
  هذه الملاحظة تحديدًا فقط — دون إنشاء أي حساب دائم له. عند إغلاق حالة استعادة
  الخدمة المرتبطة، تُرسَل له رسالة نصية تلقائية تُعلمه بأن ملاحظته عولجت.
- PROMs: كتالوج أدوات (PHQ-9، GAD-7، VAS، وPROMIS Global Health-10 مجانية
  وفعّالة؛ Oxford Knee، EQ-5D-5L، ODI، Catquest-9SF، SF-36 كـ Metadata محجوبة
  البنود حتى توثيق الترخيص)، مسارا رعاية "استبدال مفصل الركبة" و"آلام أسفل
  الظهر" (متوافق مع ICHOM) بنقاط قياس متعددة، وحساب دلتا التحسن مقابل الحد
  السريري MCID. راجع [`docs/SAUDI_PROM_ALIGNMENT.md`](docs/SAUDI_PROM_ALIGNMENT.md).
  **حلقة تشغيل كاملة**: إنشاء حلقة رعاية (Episode) من اللوحة أو عبر Webhook
  نظام المستشفى يُولّد تلقائيًا كل التكليفات (Assignments) بتواريخ استحقاقها؛
  لوحة "التكليفات المستحقة" ترسل رابط تعبئة فعلي (SMS) للأدوات المجانية فقط؛
  والمريض يعبّي الأداة عبر رابط عام (`/p/:token`) يُحتسب فيه النتيجة والفرق
  عن القياس الأساسي وتجاوز MCID تلقائيًا عند الإرسال.
- سجل تدقيق (Audit Trail) لكل عملية حساسة.
- استوديو استبيانات لإرسال دعوات بالجملة، ومركز بيانات لعرض سجل التدقيق.
- **صفحة الإدارة** (لمدير النظام فقط): إدارة الأقسام (إضافة/تعديل/إيقاف)،
  المستخدمين (إضافة/تغيير الصلاحية/إيقاف — دون إمكانية إيقاف حسابك الخاص)،
  وبنك الأسئلة (إضافة محاور وأسئلة جديدة تُلحق تلقائيًا باستبيان الخدمة
  المناسب، وإيقاف أي منها يخفيه فورًا من الاستبيان الحي والتقارير).

## التشغيل

يتطلب **Node.js 22.5 أو أحدث** بسبب استخدام `node:sqlite`.

```bash
cp .env.example .env
npm install
npm run dev
```

ثم افتح:

```text
http://localhost:3000
```

أو على macOS، انقر مرتين على `RUN_ME.command` (يثبت الاعتماديات تلقائيًا في أول تشغيل).

## خصوصية التعليقات (PDPL)

كل تعليق نصي من المريض يمر أولًا عبر طبقة إخفاء هوية محلية (`server/comments.ts`)
تزيل أرقام الجوال، الهوية الوطنية، رقم الملف، والبريد الإلكتروني، **قبل** أي
تحليل. التحليل نفسه محلي بالكامل (قواعد Rule-Based) في هذا الإصدار — لا يُرسل أي
نص إلى أي API خارجي. عند الرغبة مستقبلًا بربط نموذج ذكاء اصطناعي خارجي، يجب أن
يُطبَّق عبر واجهة `CommentAnalyzer` نفسها، وأن يتلقى فقط `redactedText` وليس
النص الخام أبدًا.

## الإعدادات والربط الخارجي (لكل مستشفى)

من **الإعدادات** في لوحة التحكم (SystemAdmin فقط)، كل مستشفى يهيّئ اتصالاته بنفسه —
بدون أي متغيرات بيئة أو إعادة نشر:

- **مزوّد الرسائل (SMS/WhatsApp)**: اختيار المزوّد (وضع تجريبي بدون إرسال فعلي، أو
  Unifonic)، مفتاح API، اسم المرسل، واللغة الافتراضية للرسائل — مع زر لإرسال رسالة
  تجريبية والتأكد من الإعدادات قبل الاعتماد عليها. عند إرسال دعوات بالجملة، يُبنى
  رابط الاستبيان تلقائيًا ويُرسل عبر `server/sms.ts` (`ConsoleSmsProvider` افتراضيًا
  — يسجّل فقط ولا يتصل بأي شبكة خارجية، حتى يُفعَّل مزوّد حقيقي).
- **Webhook للربط مع نظام المستشفى (HIS/EMR)**: توليد مفتاح API خاص بالمستشفى،
  يُستخدم من `POST /api/webhooks/invitations` لإرسال دعوات استبيان تلقائيًا عند
  خروج كل مريض دون تدخل بشري. المفتاح يُعرض مرة واحدة فقط عند التوليد (لا يُخزَّن إلا
  كـ Hash)، ويمكن تعطيله أو توليد مفتاح جديد في أي وقت.

## قبل الإنتاج

هذه نسخة **Pilot** تعمل محليًا، وليست اعتمادًا نهائيًا للنشر السريري. قبل أي نشر إنتاجي حقيقي يجب:

- ترحيل قاعدة البيانات من SQLite إلى PostgreSQL وتطبيق Row-Level Security فعليًا.
- استخدام SSO/MFA ومدير أسرار مركزي بدلًا من كلمة سر جلسة واحدة في `.env`.
- تشغيل تقييم أثر حماية البيانات (DPIA) ومراجعة PDPL وسياسة الاحتفاظ بالبيانات.
- تشفير النسخ الاحتياطية والمرفقات، وربط السجلات بنظام SIEM.
- إجراء اختبار اختراق مستقل قبل أي استخدام مع بيانات مرضى حقيقية.
- الحصول على تراخيص أدوات PROMs المقيّدة (Oxford Knee، EQ-5D-5L، ODI، Catquest-9SF، SF-36) قبل تفعيلها.
- **الإرسال الفعلي للرسائل**: طبقة `server/sms.ts` وواجهة الإعدادات جاهزتان،
  و`UnifonicSmsProvider` مبني بشكل كامل على توثيق واجهة Unifonic REST API — لكنه
  **لم يُختبر مقابل حساب Unifonic حقيقي** في هذه البيئة (لا تتوفر بيانات اعتماد
  حقيقية هنا). يجب على كل مستشفى إدخال مفتاح API الخاص به من الإعدادات، ثم التأكد
  من نجاح "الإرسال التجريبي" قبل الاعتماد عليه فعليًا.
- **الربط مع أنظمة المستشفى (HIS/EMR)**: الـ Webhook (`POST /api/webhooks/invitations`
  مع `X-Api-Key`) يعمل ويُختبر آليًا، لكنه تكامل مبسّط (JSON بسيط) وليس معيار
  HL7/FHIR القياسي؛ ربط فعلي مع نظام HIS كبير (Cerner, InstaHMS...) عادة يحتاج
  محولًا (Adapter) إضافيًا حسب تنسيق بيانات ذلك النظام تحديدًا.
- **إدارة الأقسام/المستخدمين/بنك الأسئلة من الواجهة**: حاليًا التخصيص الأساسي يتم
  تلقائيًا وقت تسجيل المستشفى (`provisionTenantDefaults`)؛ شاشات تعديل حية (CRUD)
  لإضافة/تعديل الأقسام والمستخدمين والأسئلة بعد التسجيل من لوحة التحكم لم تُبنَ بعد.
